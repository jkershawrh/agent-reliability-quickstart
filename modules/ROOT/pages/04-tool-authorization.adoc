= 4. Deny an unauthorized tool

An agent can suggest a useful plan while still requesting an action it is not
allowed to perform. This scenario separates tool selection from authorization.

== What you will learn

* Distinguish an MCP tool catalog from permission to execute a tool.
* Prove that a requested destructive operation is denied.
* Verify that OpenShift identity remains an independent backstop.
* Explain why prompt instructions cannot grant platform privileges.

== See: Two authorization boundaries

The reliability profile contains an explicit allowlist of read-only evidence
tools: alarm lookup, telemetry lookup, and runbook lookup. A repair tool is not
present, so the orchestrator must deny it before execution.

OpenShift provides a second boundary. The application service account can read
the local guardrail Service, but it cannot create Deployments, change cluster
networking, or read cluster-wide resources.

These controls answer different questions:

* the allowlist asks whether the application permits this tool;
* RBAC asks whether the workload identity may perform the platform operation;
* human approval asks whether an operator accepts the recommendation.

No model completion can change those answers.

== Do: Request a destructive action

In *Reliability Advisor*, select *Unauthorized tool request*. The case should
move to `denied` before evidence or inference. Expand the structured evidence
and locate `delete_network_config` under requested tools while executed tools
remain empty. Then prove both authorization layers in Terminal.

Submit the lab-only unauthorized-tool scenario.

[source,bash,role="execute"]
----
test -n "$ROUTE" || ROUTE="https://$(oc get route ar -o jsonpath='{.spec.host}')"
curl -fsS "$ROUTE/api/v1/advise" -H 'content-type: application/json' \
  -d '{"query":"Repair the network now","failure":"unauthorized_tool"}' \
  | tee /tmp/unauthorized-tool.json | jq
----

The advisor should explain that the requested operation is outside its allowed
tool set. It must not fabricate a successful repair.

=== Verify

Assert the application policy result.

[source,bash,role="execute"]
----
jq -e '
  .outcome == "denied" and
  (.executed_tools | length == 0) and
  .human_approval_required == true
' /tmp/unauthorized-tool.json
----

Then verify the platform boundary directly.

[source,bash,role="execute"]
----
NS="$(oc project -q)"
oc auth can-i --as="system:serviceaccount:${NS}:agent-reliability" create deployments
oc auth can-i --as="system:serviceaccount:${NS}:agent-reliability" get nodes
----

Both checks must return `no`. The warning that nodes are cluster scoped is
informational; `no` is the expected proof of isolation.

Compare the denied response with the healthy response. Evidence tools may run
for the healthy diagnosis, while no tool runs for the unauthorized operation.

== Trace intent versus authority

The response should preserve the requested tool even though execution was
denied. That is useful audit evidence: the system records intent without
pretending that the action happened.

[source,bash,role="execute"]
----
jq '{requested_tools, executed_tools, policy_decisions, model_status, trace_id}' \
  /tmp/unauthorized-tool.json
----

Expect `delete_network_config` in `requested_tools`, an empty
`executed_tools`, a tool-allowlist denial, and `not_called` model status. The
request is rejected before evidence gathering and inference because no later
reasoning can make a forbidden capability acceptable.

[cols="2,3,3",options="header"]
|===
|Layer |Question |Expected result
|Model |Can text request a repair? |Yes; text can express any intent
|Application policy |Is the repair tool in the allowlist? |No; deterministic denial
|OpenShift RBAC |Can the service account create a Deployment or read nodes? |No; independent platform denial
|Human process |May an operator perform an approved action elsewhere? |Only through the authorized operational process
|===

== Explore the positive boundary

Least privilege should not mean that every capability fails. Confirm that the
same service account can perform the narrow discovery action required by the
application while destructive permissions remain absent.

[source,bash,role="execute"]
----
oc auth can-i --as="system:serviceaccount:${NS}:agent-reliability" get services -n "$NS"
oc auth can-i --as="system:serviceaccount:${NS}:agent-reliability" create deployments -n "$NS"
----

The expected pair is `yes` followed by `no`. This positive-and-negative check
is stronger than proving only denial: it shows the identity is usable for its
declared purpose without receiving broad privilege.

In a production integration, each write-capable tool would also need input
validation, target scoping, approval context, idempotency, audit logging, and a
rollback strategy. Keeping this lab read-only makes the authorization boundary
unambiguous.

== Key takeaway

Tool availability is not tool authorization. A reliable agent combines a
small application allowlist with least-privilege OpenShift identity and keeps
the final operational decision with a human.
