= 1. Establish the healthy baseline
:imagesdir: ../assets/images

The first run establishes what a trustworthy recommendation looks like before
you introduce failures. You are the NOC operator responsible for alarm
`NOC-1042`; the advisor may recommend an action, but it cannot authorize one.

== What you will learn

* Trace one request across policy, tools, inference, and evidence validation.
* Distinguish a model recommendation from an approved operational action.
* Recognize the evidence fields required for a healthy response.
* Use a trace ID to connect an answer to its supporting decisions.

== See: The evidence-backed request path

The API receives the incident question and applies the input guardrail first.
An allowed request enters the orchestrator, which can call only the MCP tools
listed in the reliability profile. Those tools return simulated alarm,
telemetry, and runbook records. The shared MaaS endpoint reasons over that
bounded context. The application then validates the evidence before returning
the recommendation.

The request crosses four deliberately separate boundaries:

. The guardrail decides whether the input may proceed.
. The MCP allowlist decides which evidence tools may be called.
. The model proposes a diagnosis from the returned evidence.
. The application requires human approval before any operational action.

This separation matters because a fluent model response is not authorization.
OpenShift identity, application policy, and human review remain authoritative.

The same response carries two kinds of information. The recommendation is
probabilistic content intended for an operator. The decision metadata is the
machine-checkable record of how the application handled the request.

[cols="2,3",options="header"]
|===
|Response field |Reliability question answered
|`outcome` |Did the service recommend, abstain, deny, or degrade?
|`evidence` |Which alarm, telemetry, and runbook records support the answer?
|`requested_tools` |What capability did the request ask the orchestrator to use?
|`executed_tools` |Which tools actually ran after policy evaluation?
|`policy_decisions` |Which deterministic controls allowed or denied progress?
|`model_status` |Was inference available, unavailable, or never called?
|`trace_id` |How can this request be correlated with later evidence?
|`human_approval_required` |Can the recommendation become an action automatically?
|===

Do not evaluate the recommendation while ignoring its metadata. Reliability is
the combination of useful content and a provable execution path.

== Do: Run the healthy workflow

Open *Reliability Advisor*. Keep the default NOC request, select *Healthy
evidence-backed request*, and run it. The summary should show outcome
`recommended`, model `available`, three executed evidence tools, three evidence
records, human approval `true`, and a trace ID. Expand *Structured decision
evidence* to see the complete contract.

Now use *Terminal* to prove that the visual summary came from the same API.

Confirm that your terminal is already scoped to the seat namespace. Then find
the short application Route and submit the simulated NOC alarm.

[source,bash,role="execute"]
----
test -n "$(oc project -q)"
NS="$(oc project -q)"
echo "Seat namespace: $NS"
ROUTE="https://$(oc get route ar -o jsonpath='{.spec.host}')"
curl -fsS "$ROUTE/api/v1/advise" -H 'content-type: application/json' \
  -d '{"query":"Diagnose NOC-1042 and recommend the safest next step"}' | tee /tmp/healthy.json | jq
----

The command saves the complete response so later checks do not depend on
copying values by hand.

Before interpreting it, inspect the deployed components and their readiness:

[source,bash,role="execute"]
----
oc get deployment,pod,service,route
oc get deployment agent-reliability \
  -o custom-columns=NAME:.metadata.name,READY:.status.readyReplicas,IMAGE:.spec.template.spec.containers[0].image
----

You should find the advisor and the read-only NOC evidence MCP service. Record
the immutable image reference shown by the Deployment. That reference connects
the observed behavior to a deployable artifact rather than an ambiguous tag.

Open *OpenShift Console* and navigate to *Workloads → Deployments* in your
project. Locate `agent-reliability` and `noc-evidence-mcp`. Confirm both are
available, then return to the guide. This establishes the platform view you
will revisit during disruption and qualification.

=== Verify

Run the contract assertions against the saved response.

[source,bash,role="execute"]
----
jq -e '
  .outcome == "recommended" and
  .human_approval_required == true and
  (.trace_id | length > 0) and
  (.evidence | length >= 3)
' /tmp/healthy.json
----

The command must exit with status `0`. Inspect the evidence types and confirm
that alarm, telemetry, and runbook context are present. The response must not
contain a model API key, OpenShift token, or other credential.

Produce a compact trace that separates evidence sources from policy and model
state:

[source,bash,role="execute"]
----
jq '{
  outcome,
  evidence: [.evidence[] | {source, reference}],
  requested_tools,
  executed_tools,
  policy_decisions,
  model_status,
  trace_id,
  human_approval_required
}' /tmp/healthy.json
----

The healthy path should execute the three read-only evidence tools and report
the model as available. If the environment is configured to fail closed because
an external guardrail is unavailable, the response can abstain before reaching
this point. That is not a healthy baseline; capture the policy provider and ask
the facilitator to restore the guardrail dependency.

If the request fails, inspect application health before retrying:

[source,bash,role="execute"]
----
oc get pods
curl -fsS "$ROUTE/health" | jq
----

Do not bypass a failed health check. A healthy baseline is the comparison point
for every controlled failure in the remaining modules.

Save the trace ID separately. Later modules produce new trace IDs, allowing you
to prove that each result belongs to a distinct request rather than a reused
response.

[source,bash,role="execute"]
----
jq -r '.trace_id' /tmp/healthy.json | tee /tmp/healthy-trace-id
test -s /tmp/healthy-trace-id
----

== Key takeaway

A reliable agent is not defined only by a useful answer. It produces a
traceable recommendation from bounded evidence, keeps authorization outside the
model, and makes human approval explicit.
